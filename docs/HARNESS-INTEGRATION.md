# Harness Integration — bishop-memory

## Overview

Bishop-memory is a memory service that sits outside a harness. A harness connects to it via configuration and the MCP adapter, enabling two optional operational modes:

- **Standalone** (default) — each harness owns its memory entirely. Mission IDs are derived locally from folders and logs. No network calls required. bishop-memory doesn't need to be installed or running.
- **Central** — mission IDs are allocated centrally by bishop-memory so they are unique across every harness using the same service. Journal rows are also registered with the central service. Requires bishop-memory to be running.

The harness owns the connection itself. It generates its own `.mcp.json` (project-scope MCP registration) from a configuration file, and runs a generator to create that registration whenever needed. This keeps the harness self-contained and bishop-memory pure — no reach from the service into the harness.

## What The Harness Provides

A properly set up bishop-harness contains four artifacts that enable integration:

1. **`.claude/bishop-memory.conf.example`** — Configuration template showing the options.
2. **`.claude/connect-bishop-memory.sh`** — Generator script that creates `.mcp.json` from the config.
3. **`.claude/bishop-memory.conf`** — Live per-installation config (created from the example, gitignored).
4. **`.mcp.json`** — Project-scope MCP registration (generated by the connection script, gitignored).

The harness doctrine files (`.claude/agents/bishop.md`, `.claude/skills/mission-lifecycle/SKILL.md`) already contain the logic to branch on `.claude/bishop-memory.conf`: if the file exists and `BISHOP_MEMORY_MODE=central`, they use central ID allocation; otherwise they derive locally. This logic is inert without the config file, so harnesses can ship with the doctrine baked in — no patching needed, and no stale generated content.

## What bishop-memory Provides

- **HTTP API** (`cmd/memoryd`) — the core service, listening on loopback by default.
- **MCP adapter** (`cmd/mcpd`) — a stdio server proxying the HTTP API to Claude Code.
- **Reconciler** (`scripts/reconcile-memory.py`) — syncs Markdown memory state into the service's database.
- **Daemon installers** (`scripts/install-daemon.sh`, `scripts/install-daemon-linux.sh`) — runs the service as a managed system service.

## The Configuration File: `.claude/bishop-memory.conf`

This file is the single switch that controls how a harness relates to bishop-memory.

**When absent or contains `BISHOP_MEMORY_MODE=standalone`:**
- Mission IDs are derived locally.
- The harness operates entirely self-contained.
- No network calls to bishop-memory are made.
- bishop-memory doesn't need to be installed.

**When present and contains `BISHOP_MEMORY_MODE=central`:**
- Mission IDs are allocated by calling the service.
- Journal rows are registered with the service.
- Post-mission hooks mirror state to bishop-memory.
- bishop-memory must be running and reachable.

### Config File Contents

```bash
BISHOP_MEMORY_MODE=central        # or "standalone"
BISHOP_MEMORY_URL=http://127.0.0.1:8787
BISHOP_HARNESS=my-harness-name    # unique identity for this harness
BISHOP_MEMORY_HOME=/path/to/bishop-memory
```

**Why the config exists.** The MCP server registration (`.mcp.json`) sets `BISHOP_HARNESS` in the MCP process's environment. But post-mission hooks are separate shell processes invoked by Claude Code that don't inherit the MCP server's environment — they read from this config file directly. Two readers, one identity, and they must agree. The config file is the source of truth; the MCP registration echoes it.

## The MCP Registration: `.mcp.json`

The harness's `.claude/connect-bishop-memory.sh` script generates `.mcp.json` at the project root. This is a **project-scope** registration, not user-scope, and that choice is deliberate.

**Why project-scope.** Claude Code supports two registration scopes:

- **User-scope** (`~/.claude.json`) — applies to every project on the workstation.
- **Project-scope** (`.mcp.json` at project root) — applies to this project only.

If several harnesses registered bishop-memory at user scope, they would all read the same `BISHOP_HARNESS` value from the same environment variable. Central ID allocation depends on each harness having a unique identity — if they all have the same name, they collide on the same mission IDs, corrupting the journal with duplicate IDs.

Project-scope ensures each harness carries its own registration with its own `BISHOP_HARNESS` value, so collision is impossible.

**Generation vs. commitment.** `.mcp.json` holds an absolute path to the `mcpd` binary, which is per-installation and per-clone. It cannot be committed to git. Instead, the harness's generator script reads `.claude/bishop-memory.conf` and writes `.mcp.json` as needed. The generator is idempotent — re-running it detects what's already there and skips unchanged parts.

**Approval required.** In Claude Code, newly-created `.mcp.json` servers are inert until approved. After the generator runs, restart Claude Code. When prompted, approve the `bishop-memory` server. Until then, the MCP tools are unavailable.

## Why The Doctrine Lives in The Harness

The harness's `.claude/agents/bishop.md` and `.claude/skills/mission-lifecycle/SKILL.md` contain the branching logic that checks for `.claude/bishop-memory.conf` and decides between local and central ID allocation. This doctrine is inert without the config file — a harness with no `.claude/bishop-memory.conf` behaves as if the file contained `BISHOP_MEMORY_MODE=standalone`.

This design avoids the old problem: generated doctrine in bishop-memory would go stale as harnesses evolved, and its refresh path (an installer that runs in a foreign repository) becomes error-prone and hard to version. By committing the doctrine in the harness and having the config file be the only switch, doctrine stays fresh and you never need to re-generate it.

The harness never patches bishop-memory; bishop-memory never patches the harness. Both are self-contained.

## Central Mode Requires A Running Service

In central mode, an unreachable bishop-memory service is a hard stop for mission startup, not a fallback to local derivation. The reason: local derivation is right for one harness and wrong for several. Two harnesses both computing the same `NN` locally would reuse the same ID, and a reused ID in an append-only journal is ambiguous — the one thing the journal exists to prevent.

A blocked mission start is recoverable (restart the service, try again). A duplicate ID is not.

When setting up central mode, ensure bishop-memory is running and reachable before starting a mission.

## Memory Reconciliation — `scripts/reconcile-memory.py`

### What the Reconciler Does

The harness writes its memory as Markdown files. Bishop-memory holds a derived copy of that memory in its SQLite database so it can serve MCP tools and provide search. The two must stay in sync, but they can drift in two ways:

1. **During development** — if you edit FINDINGS.md, PATTERNS.md, or PROGRESS.md directly in the harness, those changes exist in Markdown but not yet in the database.
2. **On harness reconnection** — if you migrate a harness from standalone mode (where it accumulated memory locally) to central mode (where bishop-memory becomes the source of truth for some operations), the accumulated history must be copied into bishop-memory.

`scripts/reconcile-memory.py` (located in the bishop-memory checkout) syncs the Markdown truth into the database using natural-key dedupe so it is **idempotent**: running it twice changes nothing the second time.

The reconciler parses:

- `state/MISSION-ARCHIVE.md` and `state/CURRENT-MISSION.md` → creates/updates missions
- `missions/*/PROGRESS.md` → creates mission steps
- `findings/FINDINGS.md` → creates findings
- `findings/PATTERNS.md` → creates patterns
- `findings/service-records/*.md` → creates service records
- `state/FLIGHT-RECORDER.md` → creates journal events (opt-in, see below)

### Natural Key Dedupe

Each entity type has a natural key — the minimal set of fields that uniquely identifies it:

| Entity | Natural Key |
|--------|-------------|
| missions | `id` |
| mission_steps | `(mission_id, step)` |
| findings | `(finding_date, target, suggestion)` |
| patterns | `name` |
| service_records | `(agent, record_date, title)` |

The reconciler fetches the existing rows from the API, indexes them by natural key, and only creates rows that are missing. For missions, it also **updates** if `status` or `outcome` has drifted, so a Markdown edit to a mission's status is reflected in the database.

### Why Markdown Is The Source of Truth

The harness mission files (BRIEF.md, PROGRESS.md) are the primary record. They are checked into git and survive a database reset, a service crash, or a harness migration. The database is a secondary, derived copy optimized for search and MCP tool access. Syncing from Markdown → database preserves that hierarchy.

The journal (FLIGHT-RECORDER.md) is a partial exception: a post-mission hook mirrors journal rows live to the API, so the journal and database stay current during normal operation. The reconciler's journal sync is opt-in via `--include-journal` and defaults off precisely because the hook keeps it current and reconciling it can be expensive (per-mission enumeration with a 100-row cap).

### Typical Usage

After connecting a harness or editing memory Markdown directly:

```bash
cd /path/to/harness
$BISHOP_MEMORY_HOME/scripts/reconcile-memory.py --root .claude/memory
```

Verify the changes with a dry run first:

```bash
$BISHOP_MEMORY_HOME/scripts/reconcile-memory.py --root .claude/memory --dry-run
```

Where `BISHOP_MEMORY_HOME` is read from `.claude/bishop-memory.conf` in the harness.

### Flags

- `--root <path>` (required) — Path to the `.claude/memory` tree.
- `--url <url>` (optional) — Base URL of the bishop-memory API. Defaults to `http://127.0.0.1:8787`, also honoring `BISHOP_MEMORY_URL` env var.
- `--dry-run` — Parse and report what would be written; send nothing.
- `--include-journal` — Reconcile the flight-recorder (journal) as well. Default: off (the post-mission hook keeps it current).
- `--skip-steps` — Skip mission step reconciliation. Mission steps have a natural-key dedupe that excludes `status`, so a step mirrored while `in-progress` will freeze at that status when the API has no step-update path. Steps belong at the full reconciliation run during mission close, when all step statuses are final. The hook can use `--skip-steps` for live reconciliation of findings, patterns, service records, and missions; mission close runs the full reconciler without this flag. Default: off (steps are reconciled with everything else).
- `--no-sync-documents` — Skip `POST /v1/documents/sync`. Default: sync documents first so the full-text index is current in the same pass.

### The Journal Flag — Why It's Opt-In

The flight-recorder journal cannot be fully enumerated through the API (hard cap of 100 rows per request, no offset or pagination). Global dedupe is therefore impossible.

The flag is opt-in with a safety mechanism: when `--include-journal` is given, the reconciler uses per-mission enumeration with `?mission_id=<id>&limit=100`. If a mission's journal reaches exactly 100 rows, it skips that mission and warns — at the cap you cannot tell if the list is complete or truncated, and guessing risks duplicates.

In normal operation, the post-mission hook mirrors journal rows live, so the journal is already current and this flag is unnecessary. It exists only to catch rows that were missed while the service was down.

### Exit Codes

- 0 — Success (nothing to do, or all reconciliation succeeded).
- 1 — One or more operations failed (HTTP errors, validation errors).

### Idempotent First-Time Run

`scripts/reconcile-memory.py` is safe to run against a freshly-initialized database where all tables are empty, and against a populated one: it fetches existing rows, indexes them by natural key, and creates anything missing. The natural-key dedupe ensures idempotency.

This means:
- First-time setup (empty database) — works as expected, creates everything
- Subsequent runs (populated database) — creates missing rows, updates drifted fields, all idempotent

### Backward Compatibility — `scripts/backfill-memory.py`

The old `scripts/backfill-memory.py` is retained as a compatibility passthrough. It forwards its arguments directly to `reconcile-memory.py` and execs it, so the old invocation name continues to work without modification. The passthrough carries no parsing or reconciliation logic of its own — a deliberate choice to prevent the two files from drifting again as they did before the consolidation.

When you call `backfill-memory.py --root <path>`, it behaves exactly as `reconcile-memory.py --root <path>` does. For new code, call the reconciler directly; for existing scripts that reference `backfill-memory.py`, the old name keeps working.

## Connecting a Harness — From The Harness

To connect an existing bishop-harness to bishop-memory:

1. Create `.claude/bishop-memory.conf` from `.claude/bishop-memory.conf.example` in your harness, setting the mode, URL, and harness name.

2. Set `BISHOP_MEMORY_HOME` to the path of this bishop-memory checkout.

3. Run `.claude/connect-bishop-memory.sh` in your harness:

```bash
cd /path/to/my-harness
./.claude/connect-bishop-memory.sh
```

This generates `.mcp.json` and is idempotent — re-running it detects what's already there and skips it.

4. Restart Claude Code. The new `.mcp.json` server registration requires a restart.

5. Approve the server when prompted.

## Undoing the Connection

To disconnect a harness from bishop-memory:

1. Remove or rename `.claude/bishop-memory.conf` (e.g., to `.claude/bishop-memory.conf.bak`).
2. Remove the `bishop-memory` server entry from `.mcp.json` at the harness root.
3. The harness falls back to standalone mode automatically.

The doctrine files (`.claude/agents/bishop.md`, `.claude/skills/mission-lifecycle/SKILL.md`) don't need to be changed — they already branch on the presence of the config file.

## Switching Modes On An Existing Harness

If you're switching from standalone to central mode (or vice versa) on an existing harness:

1. Edit `.claude/bishop-memory.conf` and change `BISHOP_MEMORY_MODE`.
2. Re-run `.claude/connect-bishop-memory.sh` to update `.mcp.json` if needed.
3. Restart Claude Code.
4. Any existing missions keep their locally-derived IDs. New missions will be allocated from (or derived by) the service based on the new mode.
5. If migrating accumulated history to bishop-memory in central mode, run the reconciler as documented above.
